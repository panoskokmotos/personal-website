### 2. Email capture shows "✓ Sent!" even when the server fails

**What:** `_injectEmailCapture` fires the `/email-result` worker endpoint and immediately marks success without checking `res.ok`. If MailChannels rejects the message (e.g. unverified sender domain returns 400/500), users see "✓ Sent!" but never receive the email.

**Where:** `tool-utils.js:749–760`

```js
await fetch('.../email-result', { method: 'POST', ... });
this.textContent = subscribe ? '✓ Sent + subscribed!' : '✓ Sent!'; // no res.ok check
```

**Why it matters:** Users who email themselves a result — one of the only email capture hooks on the site — get false confirmation. If they don't receive the email and come back to try again, the button is permanently disabled (never re-enabled on success path). Broken loop.

**Effort:** S

**Suggested fix:**
- Check `res.ok` and show an inline error when it's falsy.
- Re-enable the button on failure so users can retry.
- Log failed email attempts in the worker's response to help debugging.

```js
const res = await fetch(...);
if (res.ok) {
  this.textContent = subscribe ? '✓ Sent + subscribed!' : '✓ Sent!';
} else {
  this.textContent = 'Failed — try again';
  this.disabled = false;
}
```

### 3. XSS in print popup via `document.write(body.innerHTML)`

**What:** `_injectPrintBtn` opens a new window and writes the raw result HTML into it using `document.write`. `formatMarkdown` only converts `**bold**` and newlines — it does not sanitize. AI responses containing inline event handlers (e.g. `<img onerror="…" src="x">`) would execute in the print window.

**Where:** `tool-utils.js:932–950`

```js
const win = window.open('', '_blank');
win.document.write(`…<div class="content">${body.innerHTML}</div>…`);
```

**Why it matters:** A crafted nonprofit name or adversarial prompt could coerce Haiku into reflecting a payload. The vector is low-probability but the remediation is trivial. Also, browser popup blockers may block the window silently if the user hasn't interacted recently.

**Effort:** S

**Suggested fix:**
- Replace `document.write` with safe DOM construction: `win.document.body.innerHTML = …` using `textContent` for unsafe portions.
- Or: sanitize `body.innerHTML` using `DOMParser` before writing — strip all `on*` attributes and `<script>` nodes.
- Also add `win?.focus()` null-guard in case the popup was blocked.

### 4. Rate-limit countdown lies — 30 s shown, actual reset is 1 hour

**What:** `_showRateLimitError` counts down 30 seconds and then hides the error message (`hideError()`), implying the user is now unblocked. The server-side rate limit in the Cloudflare Worker resets after 1 hour (`RATE_WINDOW_MS = 60 * 60 * 1000`). Users who wait 30 seconds and retry immediately hit the same 429 again.

**Where:** `tool-utils.js:205–219` (countdown timer) · `cloudflare-worker.js:107` (1-hour window)

**Why it matters:** Every rate-limited user gets a misleading countdown, retries, fails again, and likely abandons the tool completely. The mismatch erodes trust.

**Effort:** S

**Suggested fix:**
- Change the message to reflect reality: *"You've sent a lot of requests. Please try again in a few minutes or email panagiotis.kokmotoss@gmail.com directly."* — no countdown.
- Alternatively: add a `Retry-After` header in the worker's 429 response and parse it client-side.

### 5. `formatMarkdown` is too minimal for LLM output — raw markdown leaks into results

**What:** `tool-utils.js:222–226` only parses `**bold**` and newlines. Claude regularly returns structured responses with `# headers`, `## subheadings`, `- bullet lists`, and `1. numbered lists`. None of these render — users see raw `#`, `##`, and `-` characters mixed into the result text.

**Where:** `tool-utils.js:222–226`

```js
function formatMarkdown(text) {
  return text
    .replace(/\*\*(.+?)\*\*/g, '<strong>$1</strong>')
    .replace(/\n/g, '<br>');
}
```

**Why it matters:** All 11 tool results look half-broken. Structured AI output like a 5-item comparison or a donation plan with numbered steps renders as a wall of text with `1.`, `2.`, `##` visible. First-time visitors judge the quality of the tool by this output.

**Effort:** S

**Suggested fix:**
- Add header (`#`/`##`/`###`) and list (`-`/`*`/`1.`) parsing before the `\n→<br>` step.
- Process lines before joining: convert leading `#` → `<h2>`/`<h3>`, leading `-`/`*` → `<li>` wrapped in `<ul>`, leading digits+`.` → `<li>` in `<ol>`.
- Note: the AI system prompts in individual tool pages may already discourage markdown — verify before expanding; if they do, the fix is to remove the `**bold**` conversion instead.

### 8. Follow-up chat swallows rate-limit state — double error on 429

**What:** `_injectFollowUpChat` calls `_callWorkerFallback` directly (line 1079). When rate-limited, `_callWorkerFallback` calls `_showRateLimitError()` (shows the countdown in `errorBox`) and throws with `err._shown = true`. The catch block in `ask()` ignores `_shown` and overwrites the loading bubble with `'Sorry, try again.'` — two conflicting error messages appear simultaneously.

**Where:** `tool-utils.js:1079–1083` (follow-up chat catch) · compare `tool-utils.js:700–702` (refine, which correctly checks `err._shown`)

**Why it matters:** A user who hits the rate limit while asking a follow-up question sees both the 30-second countdown in the error box AND "Sorry, try again." in the chat thread. Confusing and inconsistent with how "Refine" handles the same situation.

**Effort:** S

**Suggested fix:**
```js
} catch(err) {
  loading.innerHTML = err._shown ? '' : 'Sorry, try again.';
  if (err._shown) loading.remove();
}
```

### 9. In-memory rate limiter is per-Cloudflare-isolate, not global

**What:** `cloudflare-worker.js:105–124` stores rate limit state in a module-level `Map`. Cloudflare Workers can run in multiple isolates simultaneously — each with its own clean `Map`. Under any real traffic, a user effectively gets 20 × N requests per hour where N is the number of active isolates.

**Where:** `cloudflare-worker.js:104–124`

**Why it matters:** The rate limiter provides zero meaningful protection against a visitor scripting the API. API costs (Anthropic Claude Haiku) are exposed. The personal email notification endpoint is also only protected by the cheap secret — an attacker can spam email notifications without hitting the per-isolate limit.

**Effort:** M

**Suggested fix:**
- Use the already-configured `TOOL_CACHE` KV namespace for rate limiting: write `rate:${ip}` with an expiration TTL matching `RATE_WINDOW_MS` and an atomic increment.
- If KV is not bound, fall through to the current in-memory fallback with a log warning.

### 11. Charity autocomplete renders unsanitized ProPublica data via `innerHTML`

**What:** `_initCharityAutocomplete` (tool-utils.js:1409–1414) builds dropdown HTML using template literals with `o.name`, `o.city`, `o.state`, `o.ein` from the ProPublica API — all injected into `innerHTML` without escaping.

### 12. `_injectExplainTooltips` accumulates global click listeners on every result refresh

**What:** `_injectExplainTooltips` (tool-utils.js:1504–1507) adds `document.addEventListener('click', …, { once: false })` for every heading tooltip. It uses `once: false`, so each listener is permanent. The function is called by `_injectResultExtras` after every `showResult()`, including after refine. After a few refines, dozens of stale listeners pile up.

**Where:** `tool-utils.js:1504–1507`

**Why it matters:** Each listener holds a closure over `tip` and `h`. On slow devices or long sessions this causes observable memory growth and increases the cost of every click event on the page.

**Effort:** S

**Suggested fix:**
- Change to `{ once: true }` — the listener auto-removes after the first click, which is the only time it needs to fire (hiding an open tooltip).
- Or: use a single delegated listener on `document.getElementById('result')` rather than per-heading listeners.

**What:** Everything from streaming API calls, loading skeletons, rating widgets, history drawers, share-image canvas, embed generators, charity autocomplete, voice input, keyboard shortcuts, offline restore, and PWA install prompts lives in a single file loaded on every tool page.

**Where:** `tool-utils.js` (entire file)

### 17. Biased shuffle for follow-up chips

**What:** `chat.js:100` shuffles `followUpChips` with `followUpChips.sort(() => 0.5 - Math.random())`. This is a well-known biased shuffle — the last chip in the array appears disproportionately often.

**Where:** `chat.js:100`

**Effort:** S

**Suggested fix:** Use a Fisher-Yates shuffle on a copy of the array:
```js
const shuffled = [...followUpChips].sort(() => Math.random() - 0.5); // quick fix
// proper: for (let i = arr.length - 1; i > 0; i--) { const j = Math.floor(Math.random() * (i+1)); [arr[i], arr[j]] = [arr[j], arr[i]]; }
```
